# Дашборд и Nextcloud на своём домене — инструкция владельцу

Что получится в итоге: `https://yl26.<домен>` открывает дашборд статистики, `https://cloud.<домен>` —
Nextcloud с резюме, оба с нормальным сертификатом, и при этом **на сервере не открыт ни один
входящий порт**. Трафик приходит через Cloudflare Tunnel: контейнер `cloudflared` сам
устанавливает исходящее соединение к Cloudflare, а Cloudflare терминирует HTTPS и передаёт
запросы внутрь docker-сетей по простому HTTP.

Зачем домен вообще: кнопка входа в дашборд (Telegram Login Widget) работает только по HTTPS на
домене, зарегистрированном в BotFather. IP-адрес и самоподписанный сертификат не подходят.

## Где что

- Сервер бота: `ssh leafye` (алиас с ProxyJump через is-hosting; Tailscale-адрес
  `100.106.218.33` тоже жив, но `ssh leafye` — рабочий путь с 02.09). Docker работает без sudo;
  ufw/iptables трогать не нужно и нечем — пароля sudo нет, и он не требуется.
- **Сначала — тест-стенд** `/home/leaf/YouLead26-test/` (бот `@YouLead_test_bot`), решение D-20.
  Прод `/home/leaf/YouLead26/` — только после того, как всё проверено на тесте. Перед любым
  `docker compose up` — `pwd`, чтобы не поднять не тот стек.
- Туннель `leafye` в Cloudflare Zero Trust уже создан — но коннектор `cloudflared` работает **на
  is-hosting**, не на сервере бота (см. карту схемы ниже и шаг 2).
- Сеть `edge` (подсеть `172.31.0.0/16`) существует в docker на leafye, но в маршрутизации
  трафика больше не участвует — см. шаг 1.
- Имя `dashboard` на сервере занято чужим проектом (`/home/leaf/dashboard/`, сеть
  `dashboard_default`). Наш сервис — `yl26-dashboard`, контейнер `youlead26-dashboard`.

**Карта схемы (с 31.08.2026, актуально):** коннектор `cloudflared` живёт не на сервере бота
(leafye), а на отдельной зарубежной машине **is-hosting** (`37.1.217.149`, systemd-сервис,
туннель `leafye`, remote-managed по токену). Origin'ы (дашборд, Mini App) доезжают до is-hosting
обратным ssh-туннелем с leafye: контейнер `/home/leaf/tunnel-relay` (autossh, ключ
`/home/leaf/.ssh/id_tun`). На leafye наружу не открыт ни один порт — сервисы публикуются только
на loopback (`127.0.0.1:PORT`). Заход на leafye — `ssh leafye` (алиас с ProxyJump через
is-hosting). Шаги 1–3 ниже написаны под эту схему; шаг 11а — свёрнутая историческая справка,
почему схема поменялась.

Плейсхолдеры: `<домен>` — ваш домен в Cloudflare (например `alekseev.info`), `<IP>` — адрес
сервера, с которого сейчас раздаётся Nextcloud.

## Шаг 1. Порт на loopback (вместо сети `edge`)

Сеть `edge` осталась в `docker-compose.yml` репозитория и в сторожевых тестах как наследство
прямой схемы (коннектор на leafye, origin в общей docker-сети) — ничего не стоит, но трафик
сегодня идёт не через неё. Для нового стека сеть `edge` заводить/подключать **не нужно**.

Что действительно нужно — свободный порт на loopback leafye и публикация
`127.0.0.1:<порт>:8000` в `docker-compose.override.yml` стека (не в общем `docker-compose.yml`
репозитория — он общий для всех стеков). Проверить, что порт свободен:

```bash
ss -ltnp | grep -E ':80[0-9][0-9]'
```

`DASHBOARD_TRUSTED_PROXIES=172.31.0.0/16` при этом остаётся рабочим значением, хотя сеть `edge`
в маршруте не участвует: это значение сегодня несёт живой `yl26-dashboard`, и новый стек просто
копирует его же, а не подбирает заново по коду.

**Проверка:** `ss -ltnp | grep -E ':80[0-9][0-9]'` не показывает нужный порт (свободен) до того,
как стек его займёт; после `docker compose up -d` — показывает, и `docker network ls | grep edge`
на итоговую схему уже не влияет.

## Шаг 2. Туннель — уже создан, поднимать заново не нужно

Туннель `leafye` уже создан и работает — но **на is-hosting**, не на leafye. `cloudflared` на
leafye поднимать НЕ нужно: `docker compose up` для `cloudflared` в этой схеме не выполняется
нигде на сервере бота, токен туннеля живёт на is-hosting и в репозиторий не попадает.

Если нужно завести туннель с нуля (новый is-hosting или туннель пришлось пересоздать) —
Cloudflare → Zero Trust → **Networks → Tunnels → Create a tunnel → Cloudflared**, имя например
`leafye`; установщик выполняется на is-hosting, а не на leafye.

**Проверка:** `ssh ishost systemctl status cloudflared` — статус `active (running)`; в панели
Zero Trust туннель показывает **HEALTHY**.

## Шаг 3. Проброс порта → `/etc/hosts` → Public Hostname (три подшага по порядку)

Публикация нового origin'а — это три действия в правильном порядке: сначала физический канал
(релей), потом имя (is-hosting резолвит по `/etc/hosts`), потом маршрут в Zero Trust.

**(а) На leafye — проброс порта в релее.** Дописать строку `-R 127.0.0.1:<порт>:127.0.0.1:<порт>`
в `/home/leaf/tunnel-relay/docker-compose.yml` к уже существующим и пересоздать контейнер:

```bash
cd /home/leaf/tunnel-relay && docker compose up -d --force-recreate
```

⚠️ Это короткий разрыв **всех** туннелей (и yl26, и уже развёрнутых стеков), не только нового
порта — пересоздание одного контейнера `tunnel-relay` рвёт все `-R`-мэппинги разом. Делать в
тихое время, не во время активной регистрации.

Например, для дашборда РилТолк (порт 8002) добавленная строка выглядит так:
`-R 127.0.0.1:8002:127.0.0.1:8002 tun@37.1.217.149` — рядом с уже существующими
`-R 127.0.0.1:8000:127.0.0.1:8000 -R 127.0.0.1:8001:127.0.0.1:8001`.

**(б) На is-hosting — имя в `/etc/hosts`.** Ingress в Zero Trust ссылается на имена, а не на
`localhost` — значит, имя должно резолвиться локально на is-hosting:

```bash
ssh ishost
sudo sh -c 'echo "127.0.0.1 <имя-контейнера>" >> /etc/hosts'
```

**(в) В Zero Trust — Public Hostname.** Тот же туннель `leafye` → вкладка **Public Hostname →
Add a public hostname**: `<поддомен>.<домен>` → `http://<имя-контейнера>:<порт>`. DNS CNAME
Cloudflare создаёт сам — руками в DNS ничего добавлять не нужно; оранжевое облако здесь штатно.

Домен `yl26` делится между двумя сервисами (дашборд и Mini App, Phase 19) по пути запроса — для
одного хоста заводятся ДВЕ записи, и **порядок между ними важен**: правило с `Path` обязано
стоять **выше** правила без `Path` (catch-all) — Cloudflare матчит правила сверху вниз и
останавливается на первом совпадении; если правило `/app` окажется ниже catch-all, оно никогда
не сработает и весь `yl26.<домен>` уйдёт на дашборд. В UI правила одного хоста перетаскиваются
мышью — после добавления второй записи проверить порядок.

Таблица маршрутов актуальна на 05.09.2026 (пять записей; `rt26`/`su26` заведены в этот день):

| # | Subdomain | Domain    | Type   | Path            | URL                          |
|---|-----------|-----------|--------|-----------------|------------------------------|
| 1 | `yl26`    | `<домен>` | `HTTP` | `^/app(/\|$)`   | `miniapp:8001`                |
| 2 | `yl26`    | `<домен>` | `HTTP` | *(пусто)*       | `yl26-dashboard:8000`         |
| 3 | `cloud`   | `<домен>` | `HTTP` | *(пусто)*       | `nextcloud-app:80`            |
| 4 | `rt26`    | `<домен>` | `HTTP` | *(пусто)*       | `realtalk26-dashboard:8002`   |
| 5 | `su26`    | `<домен>` | `HTTP` | *(пусто)*       | `skillup-dashboard:8003`      |

URL — имя docker-сервиса (не контейнера docker-демона leafye, а именно то имя, что записано в
`/etc/hosts` на is-hosting) и порт, без `http://` и без слэша. У записей без `Path` дополнительные
настройки не нужны.

✅ Проверено 02.09.2026: поле `Path` принимает regex как есть — `^/app(/|$)` вводится буквально,
без экранирования; панель показывает его в колонке Path и матчит корректно.

Для тест-стенда, если дашборд поднимается там, — свой поддомен (например `yl26-test`) и своё имя
в `/etc/hosts`; на момент написания на тест идёт именно `yl26.<домен>` (D-20), прод получит домен
позже.

**Проверка подшага (а)+(б) — до правила в панели:** на is-hosting
`curl -sI http://<имя-контейнера>:<порт>/health` отдаёт `200` ещё до того, как заведено правило в
Zero Trust. Если это работает, а снаружи `https://<поддомен>.<домен>` отдаёт 502 — дело в ingress
(подшаг в), а не в релее или стеке.

**Проверка подшага (в):** в разделе DNS домена появилась CNAME вида `<id>.cfargotunnel.com`
(правило `Path` отдельной DNS-записи не создаёт — это маршрутизация внутри одного хоста). Пока
стек не поднят, `https://<поддомен>.<домен>` отдаёт 502 от Cloudflare — это ожидаемо до шага 4.

**Дополнительный чек-пункт (одноразово на зону): Bot Fight Mode выключен.** В панели Cloudflare
зоны домена → **Security → Bots** — тумблер **Bot Fight Mode** должен быть **выключен**. Mini App
открывается внутри Telegram (WebView/iframe), а не в обычном браузере: включённый Bot Fight Mode
отдаёт такому клиенту HTML-челлендж вместо JSON-ответа API, и обойти это правилами WAF нельзя —
челлендж не проходится программным клиентом ни при каких настройках правил.

## Шаг 4. Стек бота: sidecar дашборда

В каталоге стека (**сначала тест**: `cd /home/leaf/YouLead26-test && pwd`) дописать в `.env`:

```
DASHBOARD_PUBLIC_URL=https://yl26.<домен>
DASHBOARD_SESSION_SECRET=<длинная случайная строка>
DASHBOARD_BOT_USERNAME=YouLead_test_bot
DASHBOARD_TRUSTED_PROXIES=172.31.0.0/16
DASHBOARD_DB_PATH=/app/data/forum.db
```

Секрет сгенерировать так: `python3 -c "import secrets; print(secrets.token_urlsafe(48))"`.
Свой на каждый стек, смена значения разлогинивает всех.

Затем:

```bash
git pull
docker compose up -d --build
```

Дашборд работает от UID 1000 и читает `data/` только на чтение (подключение `mode=ro`; том при этом
без `:ro` — WAL требует `-shm`); если папки создавались от root,
права поправить без sudo одноразовым контейнером (проверенный на этом сервере приём):

```bash
mkdir -p data logs
docker run --rm -v "$PWD/data:/d" -v "$PWD/logs:/l" alpine chown -R 1000:1000 /d /l
```

**Проверка:** `docker compose ps` — `bot` и `yl26-dashboard` в статусе `running`;

```bash
docker compose exec yl26-dashboard python -c "import urllib.request; print(urllib.request.urlopen('http://127.0.0.1:8000/health').status)"
```

печатает `200`; `https://yl26.<домен>/login` открывается в браузере со страницей входа.

## Второй ивент: дашборд = конфигурация, не форк

Дашборд — один и тот же образ `dashboard/` на все мероприятия. Второй, третий и любой
следующий экземпляр — это не новый код и не форк, а семь настроек в семи местах. Ниже —
сквозной чек-лист на одно новое мероприятие, с проверкой после каждого пункта.

**1) Выбрать поддомен и порт.** Таблица занятого:

| Порт | Занято |
|---|---|
| 8000 | дашборд Юлид |
| 8001 | Mini App Юлид |
| 8002 | дашборд РилТолк |
| 8003 | дашборд СкиллАп |

Следующий свободный — **8004**.

**Проверка:** `ss -ltnp | grep -E ':80[0-9][0-9]'` на leafye не показывает выбранный порт.

**2) `.env` стека — только секреты и bootstrap.** Никаких названий, цветов, логотипов — это
шаг 6. В `.env` идёт:

```
DASHBOARD_PUBLIC_URL=https://<поддомен>.<домен>
DASHBOARD_SESSION_SECRET=<новый, сгенерированный на сервере>
DASHBOARD_BOT_USERNAME=<юзернейм бота этого стека>
DASHBOARD_TRUSTED_PROXIES=172.31.0.0/16
DASHBOARD_DB_PATH=/app/data-rw/forum.db
```

`DASHBOARD_SESSION_SECRET` — свой на каждый стек, генерируется прямо на сервере
(`python3 -c "import secrets; print(secrets.token_urlsafe(48))"`), никогда не переиспользуется
с другого стека и не показывается в переписке (открытый секрет = вход от чужого имени).

**Проверка:** `grep DASHBOARD_ .env` в каталоге нового стека печатает пять строк выше, значения
не совпадают со значениями другого стека.

**3) Сервис дашборда в `docker-compose.override.yml` СВОЕГО стека.** Не в общем
`docker-compose.yml` репозитория — он общий для всех стеков, правка там подняла бы
`yl26-dashboard` на каждом стеке, который тянет этот репозиторий. Ключ сервиса —
`yl26-dashboard` (он определён в базовом `docker-compose.yml`, override его дополняет и
переопределяет). В override задать:

- свой `container_name` (например `realtalk26-dashboard`) — имена контейнеров глобальны на
  одном docker-демоне, совпадение с именем другого стека уронит соседний дашборд;
- `ports: 127.0.0.1:<порт>:8000`;
- `extra_hosts: host.docker.internal:host-gateway`;
- `HTTP(S)_PROXY`/`NO_PROXY` — те же значения, что у сервиса `bot` этого же стека, иначе
  уведомления о запросе доступа не уйдут в Telegram из контейнера дашборда;
- дополнительный том `./data:/app/data-rw`.

Зачем `data-rw`, а не просто `./data:/app/data:ro`: БД в режиме WAL требует у читателя права
создать рядом файл `-shm`, а само подключение дашборда остаётся строго на чтение
(`mode=ro` в `dashboard/db.py`) — «read-only» гарантирует код, а не права на файл.

**Проверка:** `docker compose config` в каталоге стека печатает сервис `yl26-dashboard` с
нужным `container_name`, портом и томом; `docker compose up -d` поднимает его без конфликта
имён с другими стеками (`docker ps` показывает уникальные имена).

**4) Релей и Cloudflare.** Не отдельная процедура — шаг 3 выше (проброс порта в
`tunnel-relay`, имя в `/etc/hosts` на is-hosting, Public Hostname в Zero Trust).

**5) BotFather.** `/setdomain` → бот этого стека → ровно `https://<поддомен>.<домен>`, без
пути и без слэша. Без этого шага кнопка входа менеджера молча не работает.

**Проверка:** `https://<поддомен>.<домен>/login` — кнопка Telegram открывает окно
подтверждения, а не «Bot domain invalid».

**6) Настройки — в боте, не в файлах.** Всё, что делает дашборд «своим» для мероприятия,
задаётся кнопками, не переменными окружения и не правкой кода:

- пресет оформления — «🎨 Оформление» → «🎭 Пресеты и ручки оформления»;
- логотип мероприятия — там же, «Лого»;
- название мероприятия (`event_name`) — кириллицей, как оно называется для людей;
- право «📊 Статистика» менеджерам этого стека — «👥 Роли и доступы»;
- нужные блоки дашборда — ⚙️ Настройки → 📊 Дашборд.

Ни цвета, ни название, ни логотип не попадают ни в `.env`, ни в код — иначе следующее
мероприятие снова станет форком, а не конфигурацией.

**7) Приёмка.**

```bash
curl -sI https://<поддомен>.<домен>/
```

Ожидается `302` на `/login`.

```bash
curl -s https://<поддомен>.<домен>/theme.css
```

Содержит акцентный цвет применённого пресета и **не** содержит `/app/` — на этом хосте нет
Mini App, и путь к её ассетам означал бы 404 на орнамент и логотип. Менеджер входит через
Telegram и видит цифры своей базы. Дашборды соседних стеков (Юлид, другие мероприятия) не
затронуты — открыть их и убедиться, что цифры и оформление прежние.

## Шаг 5. Nextcloud за туннелем (на тесте пропускается)

Стек Nextcloud живёт на сервере, не в репозитории. Найти его каталог:

```bash
docker inspect nextcloud-app --format '{{index .Config.Labels "com.docker.compose.project.working_dir"}}'
```

Сети трогать не нужно: `nextcloud-app` уже в `nextcloud_internal`, к которой подключён
`cloudflared`. Настраивается сам Nextcloud через `occ` (из того каталога):

```bash
docker compose exec -u www-data nextcloud-app php occ config:system:set trusted_domains 1 --value=cloud.<домен>
docker compose exec -u www-data nextcloud-app php occ config:system:set overwritehost --value=cloud.<домен>
docker compose exec -u www-data nextcloud-app php occ config:system:set overwriteprotocol --value=https
docker compose exec -u www-data nextcloud-app php occ config:system:set overwrite.cli.url --value=https://cloud.<домен>
```

Без `overwritehost`/`overwriteprotocol` Nextcloud за прокси, который терминирует TLS, начнёт
собирать внутренние ссылки с `http://`, и браузер заблокирует их как смешанное содержимое.
Индекс `1` в `trusted_domains` — следующий свободный; посмотреть текущие:
`... php occ config:system:get trusted_domains`.

**Проверка:** `https://cloud.<домен>` открывается без предупреждения браузера и без баннера
«доступ через недоверенный домен»; ссылки на страницах — `https`.

## Шаг 6. BotFather: домен для кнопки входа

В BotFather: `/setdomain` → выбрать бота этого стека (на тесте `@YouLead_test_bot`) → ввести
ровно `https://yl26.<домен>` — без пути и без слэша в конце.

При смене домена шаг повторяется, иначе кнопка входа молча ничего не делает.

**Проверка:** на `https://yl26.<домен>/login` кнопка Telegram открывает окно подтверждения, а не
«Bot domain invalid».

Этот шаг — только для запасного входа менеджера через `/login` (Telegram Login Widget). Кнопки
входа делегата и менеджера в само приложение (`web_app` в боте, Phase 19) регистрации домена в
BotFather НЕ требуют — это ограничение относится только к Login Widget, а `web_app`-кнопки
работают с любым HTTPS-адресом, который бот подставляет сам.

## Шаг 7. `.env` стека: ссылки на новый Nextcloud (после шага 5)

```
NEXTCLOUD_PUBLIC_URL=https://cloud.<домен>
NEXTCLOUD_VERIFY_TLS=true
NEXTCLOUD_CA_BUNDLE=
```

Самоподписанный CA больше не нужен — сертификат выдаёт Cloudflare. **`NEXTCLOUD_WEBDAV_URL` не
трогать:** загрузка идёт изнутри по `http://nextcloud-app:80/...`, это быстрее и не зависит от
туннеля. Затем `docker compose up -d`.

**Проверка:** пробная загрузка резюме тестовым делегатом — ссылка в таблице и в карточке начинается
с `https://cloud.<домен>`.

## Шаг 8. Бэкап и перенос старых ссылок

Старые ссылки в БД смотрят на `https://<IP>:8443/...`. Сначала бэкап — **вместе с `-wal`**:

```bash
cp data/forum.db data/forum.db.bak-$(date +%F) && cp data/forum.db-wal data/forum.db-wal.bak-$(date +%F) 2>/dev/null || true
```

Точный старый префикс взять из БД, не по памяти:

```bash
docker compose exec bot python -c "import sqlite3; print(sqlite3.connect('data/forum.db').execute('select resume_url from users where resume_url is not null limit 3').fetchall())"
```

Сухой прогон, сверить цифры, потом боевой:

```bash
docker compose exec bot python -m scripts.backfill_nextcloud_urls --old-base https://<IP>:8443 --new-base https://cloud.<домен> --dry-run
docker compose exec bot python -m scripts.backfill_nextcloud_urls --old-base https://<IP>:8443 --new-base https://cloud.<домен>
```

Меняется только префикс; токен шары и имя файла остаются. Затем из бота пересобрать основную
вкладку таблицы — колонка «Резюме (ссылка)» подтянет новые адреса.

**Проверка:** повторный `--dry-run` показывает `Найдено: 0`; случайная старая ссылка из таблицы
открывается.

## Шаг 9. Закрыть лишнее

Когда оба адреса работают через туннель, в compose Nextcloud убрать публикацию портов у
`nextcloud-caddy` (`ports:` с `80` и `8443`) и поднять стек заново — снаружи они больше не нужны,
а сейчас 80 виден из интернета.

**Проверка:** `docker ps --format '{{.Names}} {{.Ports}}'` — ни одной строки с `0.0.0.0:`.

## Шаг 11. Проверка правила `/app` (Mini App, Phase 19)

Две команды с любого компьютера (не с сервера) после шага 3 и поднятого стека:

```bash
curl -sI https://yl26.<домен>/app/health
```

Ожидается `HTTP/2 200`, в заголовках есть `content-security-policy` со `frame-ancestors`, и **нет**
`x-frame-options` — это трафик до Mini App, ему нельзя показывать XFO, иначе Telegram не встроит
его в iframe.

```bash
curl -sI https://yl26.<домен>/login
```

Ожидается `x-frame-options: deny` — это дашборд, у него защита от встраивания должна остаться, как
и раньше; если она пропала, правило `/app` съело слишком много и стало ловить чужие пути.

## Шаг 11а. Схема с relay — см. шаги 1–3

Фактическая схема публикации (коннектор на is-hosting, релей `~/tunnel-relay`, `/etc/hosts` на
is-hosting) описана в шагах 1–3 выше — дублировать её здесь не нужно.

Историческая справка: до 31.08.2026 коннектор `cloudflared` стоял на leafye, а origin
подключался напрямую по docker-сети `edge`. Из РФ соединение cloudflared с CF-edge стало жить
около минуты (нестабильный TLS до края Cloudflare), поэтому коннектор перенесли на зарубежную
машину (is-hosting), а origin теперь доезжает туда обратным ssh-туннелем — эта схема и есть
шаги 1–3.

Ловушка, которая не изменилась при переносе: `GET /app/` (со слэшем) отдаёт 404, рабочий адрес —
`/app` без слэша; именно его строит бот. Кнопки входа в приложение появляются/исчезают по
тумблеру «Mini App включён» без перезапуска: `curl /app/api/me` меняет ответ с `503 miniapp_off`
на `401 no_auth`.

## Если не получилось

| Симптом | Причина | Как проверить / починить |
|---|---|---|
| Туннель не HEALTHY | неверный или отозванный токен, либо `cloudflared` на is-hosting не запущен | `ssh ishost journalctl -u cloudflared -n 50` — есть `Unauthorized` → взять токен заново; сервис не `active` → `systemctl restart cloudflared` |
| Адрес отдаёт 502 | порт не проброшен в релее, либо имени нет в `/etc/hosts` на is-hosting, либо в ingress записано другое имя/порт | шаг 3: (а) `docker inspect tunnel-relay --format '{{.Config.Cmd}}'` на leafye — есть ли `-R` с нужным портом; (б) на is-hosting `cat /etc/hosts` — есть ли имя; (в) в Zero Trust — совпадают ли имя и порт в Public Hostname с `/etc/hosts` |
| Открывается не тот дашборд / 502 | в public hostname написано `dashboard` вместо `yl26-dashboard` (или перепутаны имена rt26/su26/yl26) | на сервере есть чужой проект с именем `dashboard` — исправить URL в CF; сверить имя в Public Hostname с именем в `/etc/hosts` на is-hosting |
| После пересоздания релея адреса не поднимаются | `autossh` не смог переподключиться (битый ключ, опечатка в `-R`) | `docker logs tunnel-relay` — ищет `Permission denied (publickey)`; сверить, что все `-R` записаны без опечаток (`127.0.0.1:PORT:127.0.0.1:PORT`) |
| Кнопка входа ничего не делает / «Bot domain invalid» | домен в BotFather не совпал с `DASHBOARD_PUBLIC_URL` | повторить шаг 6, сверить бота и адрес посимвольно |
| После входа снова страница входа | cookie не считается защищённой: дашборд не доверяет `X-Forwarded-Proto` | `DASHBOARD_TRUSTED_PROXIES=172.31.0.0/16` в `.env` стека (значение, скопированное у `yl26-dashboard`, не зависит от сети `edge`), в логе дашборда нет WARNING про `*` |
| Nextcloud: «недоверенный домен» или ссылки по `http` | не сделан шаг 5 | выполнить `occ`-команды, перезагрузить страницу |
| `PermissionError` / `unable to open database file` | `data/` не принадлежит UID 1000 | `chown` через alpine-контейнер из шага 4 |
| `/app/health` отдаёт `404` с телом `{"detail":"Not Found"}` | запрос ушёл на дашборд, а не на `miniapp` — правило пути не сработало или стоит ниже catch-all | шаг 3: проверить, что запись с `Path = ^/app(/\|$)` стоит ВЫШЕ записи без `Path` для того же хоста |
| В логе `miniapp` `readonly database` | том смонтирован `:ro`, либо папка `data/` не принадлежит UID 1000 | `docker-compose.yml::miniapp` — том должен быть `./data:/app/data` без `:ro`; `chown` через alpine-контейнер из шага 4 |

## Чего делать НЕ нужно

Старая схема с обратным прокси на сервере больше не используется, и её шаги теперь вредны:

- **не** заводить A-записи на IP сервера — DNS ведёт на туннель через CNAME, который создаёт Cloudflare;
- **не** переключать облако в «серое» (DNS only) — через серое облако туннель не работает;
- **не** открывать порты 80/443 на сервере и **не** ставить Caddy/nginx с Let's Encrypt — портов
  наружу нет, сертификат выдаёт Cloudflare;
- **не** класть в `tunnel/` никаких `config.yml`/`credentials.json` — туннель remotely-managed,
  всё в панели;
- **не** ставить второй `cloudflared` на leafye — коннектор один, и он на is-hosting;
- **не** заводить второй релей для нового порта — порт добавляется строкой `-R` в существующий
  `/home/leaf/tunnel-relay`, а не отдельным контейнером.
