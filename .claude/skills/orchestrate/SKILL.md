# Оркестратор (Cursor: Grok + Composer на механику)

Ты — оркестратор (родитель Grok). **Composer не замена Sonnet:** на обычную и сложную работу код
пишешь **ты**, без worker. Субагентов ставишь только на пул **механика**. План, проверка плана,
финал ветки — тоже **ты**.

- Механика: `worker` + обязательный `verifier`, оба с **`model: composer-2.5-fast`**.
- Обычная, сложная, план, финал ветки: **без субагента** (grok-slug в `model` не писать — лаунчер
  отвергает; пропуск `model` наследует дорогого Grok).
- Запрещены в `model` субагента: grok-slug, fable, claude-*, opus, sonnet, haiku, gemini, gpt, muse.
- Cursor: `.claude/skills/gsd-grok/SKILL.md`. Глобальные GSD-скиллы не переписываем.
- Правила проекта — CLAUDE.md, `.claude/orchestrate-project.md`.

## 0. Режим

**Без GSD** — журнал `.orchestrate/<дата>-<слаг>.md`.

**С GSD** (§10): план `/gsd-plan-phase` — **ты (Grok)**; `/gsd-execute-phase` **не вызывать**;
идёшь по PLAN.md (§1–§6); SUMMARY и `gsd-sdk query state.*` — как в execute-phase; `/gsd-verify-work`
— **ты (Grok)**.

## 1. Разбор до первой задачи

Таблица: задача → пул → файлы → команда проверки. Общие файлы — последовательно. Без команды
проверки задачу не стартуешь.

## 2. Пулы и кто исполняет

| пул | признаки (общие) | исполнение | проверка |
|---|---|---|---|
| **механика** | переименование; ключ/подпись по образцу; перевод строк; тест по готовому образцу; документация; бойлерплейт | **worker**, `composer-2.5-fast`, пачкой | **verifier**, `composer-2.5-fast` |
| **обычная** | фича/багфикс в 1–3 файлах, постanovка понятна, есть образец | **родитель Grok** | **родитель Grok** |
| **сложная** | несколько модулей; права; миграции; планировщик; безопасность; боевые данные | **родитель Grok** | **родитель Grok** |

Признаки репо — `.claude/orchestrate-project.md`. Не механика и не сложная по списку → **обычная
→ Grok**.

**Механику пачкуй:** один worker — 5–10 задач с непересекающимися файлами, одна проверка на пачку;
отдельный коммит на задачу. Провал задачи пачки → откат её коммита → эскалация на **Grok** (§6).

## 3. постановка worker (только механика)

Worker не видит историю. Дай: цель; файлы; критерии; команду проверки; решения; базовый коммит
(`git rev-parse HEAD`).

## 4. Статусы worker

`ГОТОВО` / `ГОТОВО С СОМНЕНИЯМИ` / `НУЖЕН КОНТЕКСТ` / `НЕ СМОГ` — первая строка отчёта дословно.

## 5. Проверка

**Механика:** `verifier` + `composer-2.5-fast` — обязательно. **Обычная/сложная:** проверяешь ты
после своей реализации (те же критерии: команда проверки, постановка, качество).

Вердикт verifier: `PASS` / `FAIL` (узкий / системный). Мелочи — в журнал, человеку списком.

## 6. Эскалация (только механика)

| событие | действие |
|---|---|
| FAIL узкий, первый на composer | **новый** worker `composer-2.5-fast` + вердикт |
| FAIL повторный, системный, `НЕ СМОГ` | **родитель Grok** (чинишь сам; grok-slug субагенту не давать) |
| провал на Grok по той же задаче | **стоп**, отчёт человеку |
| >5 кругов на задачу | стоп |

Журнал: `.claude/escalations.md` — `composer → composer` / `composer → grok`.

## 7–8. Параллельность и git

До 3 **composer**-worker параллельно — только механика, файлы не пересекаются; worktree сам.
Merge/push/выкат — только по команде человека.

## 9. Финал

1. Полный pytest один раз; упало — **Grok** (или механика через composer, если это чисто механический
   хвост).
2. Широкая проверка ветки — **Grok**.
3. Отчёт: задачи, пулы, кто исполнил (Grok / composer), эскалации.

## 10. Отчёт о прогоне

`.claude/orchestrate-runs/<дата>-<слаг>.md`: задачи по пулам; composer-запуски только на механику;
Grok — обычная/сложная/план/финал.

## Отговорки

| отговорка | почему нет |
|---|---|
| «Обычную на composer — дешевле» | Composer не Sonnet; обычная — Grok |
| «Субагенту grok-slug» | Лаунчер отвергает; без model — наследует Grok случайно |
| «Модель не указал» | На механике обязателен `composer-2.5-fast` |
| «execute-phase проще» | Одна модель профиля, без orchestrate |
