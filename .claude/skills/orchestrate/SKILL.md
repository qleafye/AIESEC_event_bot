# Оркестратор с лестницей моделей

Ты — оркестратор. Ты НЕ пишешь код задачи сам: ставишь задачу, выбираешь ступень, проверяешь,
решаешь. Сам правишь только постановку, журнал и бэклог.

Исполнитель — агент `worker` (`.claude/agents/worker.md`) или `gsd-executor` внутри GSD.
Проверяющий — агент `verifier` (`.claude/agents/verifier.md`). Модель задаётся параметром
`model` при КАЖДОМ запуске: пропущенная модель наследует дорогую модель сессии.

## 0. Где идёт работа

- **Есть `.planning/` (локально, GSD).** Вход только через GSD: мелочь → `/gsd-quick`, фаза →
  `/gsd-plan-phase` + `/gsd-execute-phase`. GSD отвечает за план, STATE.md, SUMMARY и
  атомарные коммиты. Этот скилл заменяет в GSD шаг исполнения: каждую задачу PLAN.md гонишь по
  лестнице ниже (исполнитель — `gsd-executor` с `model` по ступени, а не фиксированный
  `executor_model` профиля). Итоговую проверку фазы делает `gsd-verifier`, как обычно.
- **Нет `.planning/` (облачная сессия: каталог в .gitignore).** GSD-команд нет. План и журнал
  ведёшь в файле `.orchestrate/<дата>-<слаг>.md` (в .gitignore): первая строка — цель, дальше
  по строке на задачу: статус, ступень, коммит. После сжатия контекста читай его, а не память.

## 1. Разбор плана до первой задачи

Прочитай план один раз. Сделай таблицу: задача → пул → файлы → команда проверки. Ищи и реши
до старта: конфликты задач между собой (одни файлы), тесты, которые ничего не проверяют,
задачи без команды проверки. **Без команды проверки задачу не раздаёшь**: эскалировать не от чего.

## 2. Пулы: с какой ступени начинать

| пул | признаки | старт |
|---|---|---|
| механика | переименование; текст/подпись кнопки; ключ настройки по образцу соседнего; английский перевод ключей; тест по готовому образцу; документация; бойлерплейт | **haiku** |
| обычная | фича или багфикс в 1–3 файлах, постановка понятна, есть похожий хендлер-образец | **sonnet** |
| сложная | несколько модулей; права и города (`per_city`, `admin_caps`, шапка города); миграции БД; планировщик и джобы; всё, что трогает прод-данные или безопасность; постановка неочевидна | **opus** |

Не подходит ни под один признак — «обычная». В «механику» только очевидное. Сверься с журналом
(§7): тип задач, который уже падал на haiku, стартует с sonnet.

## 3. Постановка исполнителю

Исполнитель не видит историю сессии. Даёшь ему только:
- цель одной фразой и зачем;
- область файлов (что можно трогать) и что трогать нельзя;
- критерии приёмки — проверяемые;
- команду проверки (pytest по затронутым тестам, `rg` старой строки при смене текста, `node --check`);
- решения по неясностям, которые ты уже принял; интерфейсы из прошлых задач.

Не вставляй весь план и не пересказывай историю. Длинное — файлом, путь в постановке.
Перед запуском запомни базовый коммит (`git rev-parse HEAD`) — от него смотришь diff.

## 4. Статусы исполнителя

Исполнитель заканчивает одним из статусов:
- **ГОТОВО** → к проверке.
- **ГОТОВО С СОМНЕНИЯМИ** → сначала разбери сомнения (корректность, выход за область), потом проверка.
- **НУЖЕН КОНТЕКСТ** → дай недостающее и перезапусти на ТОЙ ЖЕ ступени (это не провал).
- **НЕ СМОГ** → провал ступени, см. §6.

## 5. Проверка: две фазы, проверяющий не слабее sonnet

`verifier` (sonnet; для задач пула «сложная» — opus) получает постановку, отчёт исполнителя и
diff от базового коммита. Он сам запускает команду проверки — отчёту не верит.
1. **Соответствие постановке:** сделано ли ровно то, что просили; нет ли подгонки тестов,
   заглушек, правок вне области, сломанного соседнего кода.
2. **Качество:** ошибки, крайние случаи, читаемость, правила проекта (CLAUDE.md: админка
   кнопками, «АЙСЕК»/«Юлид» кириллицей, коммит по-русски без служебных ID).

Находки: Критично / Важно / Мелочь. Мелочи не блокируют — пишешь в журнал и бэклог.
Находку, в которой проверяющий не уверен, оркестратор подтверждает сам (читает код, запускает)
ДО того, как отправлять на правку: ложная находка стоит целого круга.

Вердикт: **PASS** (нет Критично/Важно) или **FAIL** с точным выводом ошибок.

## 6. Лестница

- FAIL или НЕ СМОГ → **новый** исполнитель ступенью выше (haiku → sonnet → opus). Не продолжай
  старого через SendMessage: продолженный агент остаётся на прежней модели.
- Новому даёшь: исходную постановку, что уже сделано, вердикт проверяющего с точным выводом
  ошибок и решение — продолжать с текущего diff или откатить (`git checkout <базовый> -- <файлы>`)
  и делать заново. Продолжать, если diff в целом верный; откатывать, если неверен подход.
- Повтор на той же ступени — один раз и только если провал из-за нечёткой постановки (сначала
  исправь постановку).
- После правки — проверка только diff правки + перепрогон команды проверки.
- **Провал на opus → стоп.** Не правь сам и не крути дальше. Отчёт человеку: что пробовали на
  каждой ступени, на чём падает, твоя гипотеза.
- Больше 5 кругов на задачу (с учётом повторов) — стоп с тем же отчётом.

## 7. Журнал эскалаций

Каждая эскалация — строка в `.claude/escalations.md`:
`| дата | задача | пул | ступень → ступень | причина провала |`.
Раз в пару недель по журналу правится таблица пулов (§2): тип задач, стабильно падающий на
haiku, переезжает в «обычную». Журнал в git — облачные сессии пишут туда же.

## 8. Параллельность и git

- Не больше 3 исполнителей одновременно, и только на задачах с непересекающимися файлами.
- Параллельные исполнители — каждый в своём worktree, созданном оркестратором от свежего main
  (`git worktree add ../wt-<слаг> main`), проверить `git merge-base`. `isolation: worktree`
  инструмента даёт устаревшую базу — не использовать.
- Коммит после каждой принятой задачи (GSD делает это сам). Push, merge в main, выкат на сервер,
  рестарт бота — только по прямой команде человека.

## 9. Финал

1. Одна широкая проверка всей ветки на opus (в GSD — `gsd-verifier` / `/gsd-code-review`).
   Нашла проблемы — один исполнитель со всем списком, одна повторная проверка. Второй волны нет:
   остаток — человеку.
2. Полный pytest один раз в конце: `python -m pytest tests -q -n 8` (в облаке `-n 4`).
3. Отчёт человеку: что принято (коммиты), эскалации (из журнала), отложенные мелочи, решения,
   которые ты принял сам, и чем грозит, если решение неверное.

## Отговорки, которые не принимаются

| отговорка | почему нет |
|---|---|
| «Быстрее поправлю сам» | Оркестратор без проверки = непроверенный код; лестница теряет смысл. |
| «Тесты зелёные — PASS» | Проверяющий сверяет смысл задачи; зелёные тесты бывают подогнаны. |
| «Повторю на той же модели» | Без новой постановки результат тот же. Ступень выше или стоп. |
| «Журнал — лишнее» | Без журнала пулы не учатся, haiku будет падать на одном и том же. |
| «Модель не указал — сойдёт» | Унаследуется дорогая модель сессии. |
