## Phase Goal

**As a** DXP manager, **I want to** toggle consent and payment modules in the admin panel and have them activate immediately for new registrations, **so that** the bot works for both free forums and paid conferences without redeploying code.

**Decisions covered:** D-08 (payment-option selection), D-09 (payment step after approval), D-11 (receipt accepts PDF or photo, rejects other types), D-14 (payment is the last slice), D-15 (payment step never fires when toggle OFF).

<objective>

Creates the new handlers/payment.py file and adds a payment hook to approve_user() in registration.py. Wires the new router into main.py.

Purpose: Delivers ROADMAP SC#3: "Approved user with payment module enabled receives payment instructions (amount, bank details, deadline, penalty schedule) and can upload a receipt; non-PDF/non-photo uploads are rejected with a clear error." Also implements PAY-05 status transitions: pending→not_paid (DB default) → receipt_sent (after upload).

Output: handlers/payment.py (new), registration.py approve_user modified, main.py with payment router include and init_payment_module call.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| User → receipt upload | Untrusted file type from user; must enforce allowlist before storing file_id |
| approve_user → payment step | Payment step must only be reachable after approval; payment_enabled gate enforces this |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-04-01 | Spoofing | Receipt upload — file type forgery | mitigate | For F.document handler: check message.document.mime_type == "application/pdf"; reject with user-facing error for any other MIME type. For F.photo handler: Telegram validates photo type server-side — only actual Telegram photos can trigger F.photo filter. File stored as file_id only (never downloaded/executed). |
| T-04-04-02 | Elevation of Privilege | Payment step reachable without approval | mitigate | start_payment_step is only called from approve_user(), which is only called after the atomic approve_user_atomic DB update confirms rowcount=1. Payment module's own callbacks (pay_option:*) have no ADMIN_IDS gate — they are user-facing — but they are also effectively gated: the user must have received the option keyboard from start_payment_step to know the callback data. |
| T-04-04-03 | Denial of Service | Payment module enabled with empty/broken settings blocks user post-approval | mitigate | Fail-safe: payment_enabled defaults OFF; admin must deliberately enable. If payment_requisites is empty, _show_payment_details still sends a valid (if sparse) message. If payment_options is empty, start_payment_step treats it as a single free option and skips the selection step — user goes directly to requisites. No unhandled exception can leave the user stuck (try/except in approve_user). |
| T-04-04-04 | Information Disclosure | payment_option and payment_deadline written to users table | accept | payment_option (label like "Полный билет") and payment_deadline are not sensitive PII. payment_due is a date string. receipt_file_id is a Telegram file_id — valid only via Telegram API, not exploitable. |
</threat_model>
