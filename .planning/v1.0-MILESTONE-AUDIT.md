## Integration Blocker (HIGH)

**Party-track payment re-entry silently reverts to "full" pricing.**

- `handlers/user_actions.py:106` — `upload_receipt_entry` (the «💳 Оплата» button)
  calls `start_payment_step(bot, message.from_user.id)` **without** `participant_type`.
- Signature `handlers/payment.py:188` defaults it to `"full"`.
- Approval path (`registration.py:2245`) threads it correctly; only the re-entry path is broken.

**Break:** A party delegate who tapped «Оплачу позже» earlier, or lost FSM state on a bot
restart, taps «💳 Оплата» and is filtered against `"full"` tariffs. With track-split
`payment_options` configured (the TRACK-05 feature), either they see the **wrong (full)
price**, or — if no `track=None` fallback exists — `_visible_options` returns empty, D-18
fires, and they are **silently marked done without paying**.

**Uncovered:** no test exercises `upload_receipt_entry`/`should_offer_receipt_upload` with
`participant_type`. `handlers/user_actions.py` has zero `participant_type` references and
was not touched by any Phase 5 plan (05-01..06).

**Fix (small, ~1 file):** resolve `participant_type` via `get_user()` in
`upload_receipt_entry`, pass to `start_payment_step`; optionally gate
`should_offer_receipt_upload` on per-track `_visible_options` non-emptiness. Add a
regression test mirroring `tests/test_payment_phase5.py:148`.
