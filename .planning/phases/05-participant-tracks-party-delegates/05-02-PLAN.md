## Phase Goal

**As a** DXP manager, **I want to** configure which questions and which wording a party guest sees, separately from the full delegates, **so that** a one-night guest is not asked about their university or a three-day housing plan.

**Decisions covered:** D-03 (single __party namespace), D-04 (tri-state inherit/on/off), D-05 (per-track wording), D-07 (party preset writes only __party keys), D-08 (overnight questions reuse existing steps), D-09 (no new REG_FLOW keys).

<objective>
Make the registration engine track-aware: every question gate and every question prompt resolves through the party override namespace first and falls back to the global setting when the override key is absent. Add the overnight-only skip rule and the 🎉 Party seed preset.

Purpose: this is the behavioral core of TRACK-02. The admin UI in plan 05-03 renders exactly the tri-state this plan defines, so the resolution semantics must land first.

Output: four changes inside `handlers/registration.py` (a new tri-state resolver, a widened `_prompt`, one new rule in `_get_enabled_steps`, a party preset + apply function) plus `tests/test_registration_phase5.py`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| bot_settings (admin-written) → registration flow | Setting values control which questions are asked and what text is sent to users |
| `__party` key namespace → global key namespace | A namespace leak would let a party-side edit alter the live full-delegate flow |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-02-01 | Tampering | `_apply_party_preset` | mitigate | The function's only write is `set_setting(f"{setting_key}__party", ...)` with `setting_key` sourced from the hardcoded `REG_FLOW` list — no user-supplied key can reach `set_setting`. A test asserts zero global keys change (D-07). |
| T-05-02-02 | Elevation of Privilege | `_is_step_enabled_for_track` | mitigate | The `__party` branch is entered only when `_is_party_track(participant_type)` is True, and `participant_type` originates from the closed vocabulary enforced by `_extract_party_track` in 05-01. A full-track user cannot cause a `__party` key to be read. |
| T-05-02-03 | Information Disclosure | `_prompt` per-track wording | mitigate | Prompt text is admin-authored and sent only to the user being asked the question. `_prompt` returns text for the caller to send; it performs no interpolation of other users' data, so no cross-user leakage is possible. |
| T-05-02-04 | Denial of Service | `get_setting` calls added per step | accept | `_get_enabled_steps` adds at most one extra `get_setting` per step for party users only. Party volume is a small fraction of the 1000–1500 season total against local SQLite; the added read cost is negligible and does not warrant a caching layer. |
| T-05-02-05 | Tampering | empty-string prompt override | mitigate | `_prompt` uses truthiness for the override, so an empty `reg_prompt_<step>__party` falls back to the global text instead of sending a blank message that would strand the user on an unanswerable step. |
</threat_model>
