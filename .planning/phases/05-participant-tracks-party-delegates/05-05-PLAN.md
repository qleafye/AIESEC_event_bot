## Phase Goal

**As an** approved party guest, **I want to** see only the tariffs that apply to my night, **so that** I do not accidentally pay the three-day forum price for one evening.

**Decisions covered:** D-16 (optional third `track` field, 2-field lines still valid), D-17 (index contract preserved), D-18 (no matching tariff means free).

<objective>
Split `payment_options` by track without breaking any existing configuration and without disturbing the positional `pay_option:{i}` contract.

Purpose: this is the one place in Phase 5 where a naive implementation causes a silent money bug. Filtering the options list before enumerating it would shift indices and make an already-delivered keyboard select a different tariff than its label shows.

Output: a widened `_parse_options` plus track-aware rendering in `handlers/payment.py`, the track threaded from the approval path in `handlers/registration.py`, and `tests/test_payment_phase5.py`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `pay_option:{i}` callback → tariff selection | A client-supplied index selects the price the user is charged |
| `payment_options` setting → user-facing prices | Admin-authored text parsed into money values |
| user's `participant_type` → tariff visibility | A user-influenced value gates which prices are offered |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-05-01 | Tampering | `pay_option:{i}` index contract | mitigate | `_visible_options` emits indices from `enumerate` over the UNFILTERED list and `process_payment_option` keeps indexing that same list. A keyboard rendered before a settings edit therefore resolves to the tariff it was built from, not a shifted neighbour. Proven by a dedicated index-preservation test (D-17). |
| T-05-05-02 | Tampering | out-of-range or non-numeric `pay_option:{i}` | mitigate | `process_payment_option` must bounds-check the parsed index against the current options list and reject anything out of range with a callback answer — a crafted `pay_option:999` must not raise or select a default tariff. Verify the existing guard is present and extend it if not. |
| T-05-05-03 | Elevation of Privilege | user selecting a cheaper cross-track tariff | mitigate | The rendered keyboard is filtered by track. Residual risk: a user who retains an old keyboard from a different track could tap an index that is not currently visible to them. Disposition: accepted for this phase because indices are stable by D-17 and the exposure is limited to a user re-tapping a tariff they were legitimately offered earlier; a server-side re-check of eligibility in `process_payment_option` is recorded as a follow-up. |
| T-05-05-04 | Denial of Service | no tariff matches the track | mitigate | D-18 routes to the free completion path rather than sending an empty keyboard, so an approved user is never stranded on a screen with no actionable button. |
| T-05-05-05 | Tampering | malformed `payment_options` line | mitigate | Non-integer prices fall back to 0 and pipe-less lines parse to a labelled 0-price entry, both preserving today's behavior; no parse path raises, so a typo in the admin setting cannot break the approval flow for every user at once. |
</threat_model>
