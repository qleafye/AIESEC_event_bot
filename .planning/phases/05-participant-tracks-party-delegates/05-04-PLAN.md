## Phase Goal

**As a** party guest, **I want to** be approved on the party track's own rules and receive a welcome message about the party — not about a three-day forum, **so that** I show up at the right place at the right time.

**Decisions covered:** D-09 (no new REG_FLOW key for the fork), D-10 (fork question behind party_fork_question, suppressed by an authoritative deep link), D-13 (independent party_approval), D-14 (shared queue on manual, no queue at all on auto), D-15 (approve_text__party).

<objective>
Route party applications through their own approval setting and their own approval message, and add the optional in-flow fork question that lets a delegate self-select a track when no deep link was used.

Purpose: without this plan a party registration inherits full-delegate moderation and receives the forum welcome text — wrong dates, wrong venue, wrong price expectation.

Output: a third branch in `_decide_status`, its threading through `finalize_registration`, `_approve_text_for` wired into the approval send path, and a pre-flow fork keyboard in `cmd_start`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `party_pick:` callback → track assignment | A client-supplied callback directly selects the track that governs pricing |
| bot_settings → approval decision | `party_approval` decides whether a registration is moderated at all |
| `approve_text__party` → user message | Admin-authored text sent to approved users |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-04-01 | Elevation of Privilege | `party_pick:` callback handler | mitigate | The token is mapped through the fixed `_PARTY_TAG_MAP` and an unmapped token is rejected, so no arbitrary track value can be set. The handler additionally re-checks `party_enabled` before honouring a party choice, closing the render-then-flip window in which a user could obtain a party-priced registration after the track was closed. |
| T-05-04-02 | Elevation of Privilege | `_decide_status` party branch | mitigate | `party_setting or "manual"` means an unconfigured or unreadable `party_approval` moderates rather than auto-approves. Failing closed prevents an attacker from obtaining an unmoderated approval by racing an unset setting. |
| T-05-04-03 | Spoofing | fork bypass of the D-11a gate | mitigate | The fork is only rendered when `party_enabled == "on"`, so the closed-track path established in 05-01 cannot be circumvented by an in-flow choice. |
| T-05-04-04 | Denial of Service | `get_user` lookup in `approve_user` | mitigate | Wrapped so a lookup failure degrades to the global approve text; an approved user always receives a message and is never stranded without a main menu. |
| T-05-04-05 | Information Disclosure | `approve_text__party` content | accept | Text is admin-authored and sent only to the approved user. No registrant data is interpolated into it, so no cross-user disclosure surface exists. |
| T-05-04-06 | Tampering | double approval of a party row | mitigate | No change to the atomic `UPDATE … WHERE status='pending'` guard from Phase 2; party rows go through the same shared path, so the existing rowcount=0 double-approve guard covers them unchanged (D-14 shared queue). |
</threat_model>
