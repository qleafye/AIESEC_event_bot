## Phase Goal

**As a** party-only guest, **I want to** open the party deep link and be registered on the party track that survives a repeat `/start`, **so that** I book the night I actually want instead of silently landing in the expensive full-forum form.

**Decisions covered:** D-01 (users.participant_type migration), D-02 (two-point track persistence), D-10 (deep-link parsing, existing deep links unbroken), D-11a (master toggle + closed message + explicit fallback button).

<objective>
Deliver the first end-to-end party slice: a guest taps `t.me/<bot>?start=party_over`, the bot records `participant_type='party_overnight'` at flow start, the guest completes the existing question flow, and the finished row lands in `users` with the track set. A repeat bare `/start` mid-flow keeps the track. When `party_enabled` is off, the party link shows a closed message with an explicit opt-in button into the full flow.

Purpose: every other Phase 5 plan reads `participant_type` — this plan is the only source of that value. It also establishes the D-11a safety posture before any per-track pricing exists.

Output: Phase 5 migration block + 2 DB helpers in `database/db.py`; track extraction, master gate, and 2 persistence write points in `handlers/registration.py`; `tests/test_db_phase5.py`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Telegram `/start` payload → cmd_start | `command.args` is fully attacker-controlled free text |
| party deep link → pricing track | The track selected here determines which tariffs the user is later offered (plan 05-05) |
| init_db() → production data/forum.db | Migration runs against ~590 live user rows |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-01-01 | Tampering | `_extract_party_track` | mitigate | Exact-match lookup in a fixed 2-entry dict `_PARTY_TAG_MAP` after `.strip()`. No prefix/startswith/regex matching, so no crafted payload can produce a track value outside the closed vocabulary, and no arbitrary string reaches `participant_type`. |
| T-05-01-02 | Elevation of Privilege | `party_enabled` master gate | mitigate | The gate is evaluated before any registration-flow code and returns early. An attacker who guesses the party token while the track is closed gets the closed message only — they cannot obtain a party-priced registration (D-11a). |
| T-05-01-03 | Spoofing | `party_fallback_full` callback | mitigate | The callback starts the FULL flow only; it can never set a party track. It carries no user-supplied parameters, so a replayed or forged callback_data cannot select a track. |
| T-05-01-04 | Tampering | init_db() Phase 5 block | mitigate | `_ensure_column` (ADD COLUMN) + `DEFAULT 'full'` only. No DROP COLUMN, no INSERT OR REPLACE on `users`. Verified by a test that seeds a row before the migration and asserts it reads back intact. |
| T-05-01-05 | Denial of Service | `get_reg_started_track` in cmd_start | mitigate | Wrapped in try/except with error-level logging; a DB failure degrades to "no track recovered" and `/start` still works. Matches the established fail-soft posture for non-critical side paths. |
| T-05-01-06 | Information Disclosure | party gate logging | accept | Only telegram_id and exception text are logged, never the raw `command.args` payload — consistent with the repo's PII-safe logging convention. No new disclosure surface. |
</threat_model>
