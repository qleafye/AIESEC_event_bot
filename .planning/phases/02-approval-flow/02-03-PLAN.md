<objective>
Build the manager-facing review queue in `handlers/admin.py`: a paginated "📋 Заявки" tinder UI fed by the oldest pending DB row (D-07), with atomic Одобрить (APP-06), reason-prompted Отклонить (D-12), session-only Пропустить, resume re-send (APP-04 / QW-03 manager half), and a confirmed Одобрить все N that flips the queue atomically and welcomes each flipped user once with 429 handling (APP-05, D-11). Plus the self-documenting settings command (D-16) so a new admin can see every approval toggle and its current value.

Capability delivered: a manager opens Заявки, reviews applications one card at a time, opens attached resumes, approves/rejects with a reason, skips for later, or mass-approves the whole queue — all restart-safe (queue is DB-driven) and race-safe (no double approval, no double welcome).

Decisions covered (traceability): D-06 (Заявки entry, one card at a time). D-07 (DB-driven oldest-pending queue; Пропустить tracked in FSM, no status change). D-08 (card buttons). D-11 (Одобрить все N confirmation + flip-first/background-send with TelegramRetryAfter). D-12 (free-text reject reason, escaped). D-16 (settings-guide command).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Telegram callback → admin handlers | callback_data (incl. tid) from any chat member reaches approve/reject/skip actions |
| Manager free-text reason → applicant | reason string is forwarded into an HTML message to the applicant |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-0203-01 | EoP | every appr_* callback | mitigate | Message-level `is_admin` does NOT cover callbacks; each callback handler re-checks `callback.from_user.id in config.ADMIN_IDS` (mirrors _start_segment_broadcast) and toasts "Недостаточно прав" otherwise. |
| T-0203-02 | Race / double approval | appr_approve, appr_all | mitigate | approve_user_atomic rowcount guard + approve_all_pending single-statement flip make concurrent manager actions idempotent; approve_user is only called on a confirmed flip, so no applicant is welcomed twice. |
| T-0203-03 | XSS/HTML injection | reject reason, card fields | mitigate | reason and all card free-text are `html_module.escape`d before HTML send. |
| T-0203-04 | DoS (mass-approve send storm / 429) | _welcome_flipped | mitigate | Background send catches TelegramRetryAfter and backs off retry_after+1; the DB flip is already committed so a send failure never re-opens the queue. |
| T-0203-05 | Info disclosure | appr_resume | accept | Resume is re-sent only to the admin chat that invoked it (callback.message), behind the admin re-check. |
</threat_model>
