<objective>
Add the database layer for the approval flow to `database/db.py`: the atomic single-row approve/reject guards (APP-06), the oldest-first pending queue query and count (feed APP-04), and the bulk "approve all" flip that returns exactly the ids it changed (APP-05). This is the pure data foundation — no handlers, no UI — so the review-UI plan (02-03) and the registration-split plan (02-02) can consume stable, race-safe primitives.

Capability delivered: any caller can (a) approve one pending application atomically with a boolean "did I win the race" result, (b) reject one pending application, (c) list/count the pending queue oldest-first for pagination, and (d) approve the entire pending queue in one statement and learn precisely which users flipped so each is welcomed exactly once.

Decisions covered (traceability): D-07 (queue is DB-driven, oldest `status='pending'` first — `get_pending_users`/`get_pending_count`). D-10 (approve is atomic `UPDATE … WHERE status='pending'` + rowcount guard — `approve_user_atomic`). D-11 (mass approve flips first and returns flipped ids — `approve_all_pending` with `RETURNING`). D-12 (reject sets `status='rejected'` — `reject_user`).

<notes>
- `RETURNING` requires SQLite >= 3.35 (bundled in CPython 3.10+ on all target platforms). If a target environment pins an older sqlite, the fallback is a single transaction: `BEGIN IMMEDIATE; SELECT telegram_id WHERE status='pending'; UPDATE ... WHERE status='pending'; COMMIT` — the IMMEDIATE lock makes the snapshot atomic. Prefer `RETURNING`; document the fallback in a comment.
</notes>
