    start_payment_step(bot: Bot, telegram_id: int) — async function (not a handler, called from approve_user):
      Reads payment_options setting (newline "label|price" pairs). Parses into list of (label, price) tuples. If empty or all prices are 0, skip the option selection step and go directly to requisites display (single free option = no choice needed). Otherwise, build an InlineKeyboardMarkup with one button per option, callback_data="pay_option:{i}" where i is the 0-based index. Send message "💳 Выбери вариант участия:" with the keyboard. Bot must also set the user's FSM state — but this is called from outside an FSM handler. Solution: use bot.send_message to send the options; to set state, use a workaround: include the options payload in the message via callback and rely on the callback handler to set state. Alternatively, use a direct state set with StorageKey. However, since FSM from outside a handler is complex in aiogram 3, the simplest approach: send a "choose option" message. When user taps a button, the pay_option callback handler sets the FSM state and handles the flow. Do not set FSM state from start_payment_step — let the callback be stateless (check that user telegram_id matches callback.from_user.id implicitly via aiogram routing). This is the cleanest approach for this brownfield codebase.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| User → receipt upload | Untrusted file type from user; must enforce allowlist before storing file_id |
| approve_user → payment step | Payment step must only be reachable after approval; payment_enabled gate enforces this |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-04-01 | Spoofing | Receipt upload — file type forgery | mitigate | For F.document handler: check message.document.mime_type == "application/pdf"; reject with user-facing error for any other MIME type. For F.photo handler: Telegram validates photo type server-side — only actual Telegram photos can trigger F.photo filter. File stored as file_id only (never downloaded/executed). |
| T-04-04-02 | Elevation of Privilege | Payment step reachable without approval | mitigate | start_payment_step is only called from approve_user(), which is only called after the atomic approve_user_atomic DB update confirms rowcount=1. Payment module's own callbacks (pay_option:*) have no ADMIN_IDS gate — they are user-facing — but they are also stateless: the user must have received the option keyboard from start_payment_step to know the callback data. |
| T-04-04-03 | Denial of Service | Payment module enabled with empty/broken settings blocks user post-approval | mitigate | Fail-safe: payment_enabled defaults OFF; admin must deliberately enable. If payment_requisites is empty, _show_payment_details still sends a valid (if sparse) message. If payment_options is empty, start_payment_step treats it as a single free option and skips the selection step — user goes directly to requisites. No unhandled exception can leave the user stuck (try/except in approve_user). |
| T-04-04-04 | Information Disclosure | payment_option and payment_deadline written to users table | accept | payment_option (label like "Полный билет") and payment_deadline are not sensitive PII. payment_due is a date string. receipt_file_id is a Telegram file_id — valid only via Telegram API, not exploitable. |
</threat_model>
