## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Admin callback → payment_status write | Receipt confirm/reject changes payment_status for a real user |
| APScheduler job → user message | Scheduled reminder fires for a user who may have already paid |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-05-01 | Elevation of Privilege | rcpt_confirm / rcpt_reject / rcpt_skip / rcpt_view callbacks | mitigate | Every handler checks config.ADMIN_IDS on entry (admin.py:281 precedent, replicated verbatim). ReceiptReview.reject_reason message handler also checks message.from_user.id. |
| T-04-05-02 | Tampering | Two admins confirming the same receipt simultaneously | mitigate | update_payment_status() returns rowcount from "UPDATE ... WHERE payment_status='receipt_sent'". Only rowcount=1 triggers the confirmation message to the user and cancel_payment_reminders. rowcount=0 = already processed — handler returns early with an admin-only "already handled" answer. |
| T-04-05-03 | Spoofing | Payment reminder fires after manual admin confirmation | mitigate | send_payment_reminder() reads payment_status before sending; returns early if status is 'paid' (D-13 SC#5). cancel_payment_reminders() is called synchronously inside rcpt_confirm handler BEFORE the confirmation message is sent — the cancel happens first. |
| T-04-05-04 | Denial of Service | sweep_payment_overdue bulk-updates users with broken payment_deadline | mitigate | sweep_payment_overdue reads payment_deadline setting, returns early if absent or unparseable, returns early if deadline has not yet passed. Only marks 'not_paid' rows — 'receipt_sent' and 'paid' rows are untouched. |
</threat_model>
